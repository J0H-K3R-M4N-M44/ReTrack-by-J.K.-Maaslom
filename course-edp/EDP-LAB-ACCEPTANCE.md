# Phase 4 — EDP and browser acceptance

**Scope:** the isolated `EDP-Course-MVP` / `repairtrack_edp` academic app only. This is **not** permission to deploy or merge into `main`.

## Module 3 source requirements

From the provided **Manual — Module 3**, Activity 9 requires a GUI text editor with `OpenFileDialog`, `SaveFileDialog`, a `FileSystemWatcher` monitoring `.txt` changes, and an integration into the project. Activity 10 requires an external REST API, meaningful display of JSON, and graceful failure/timeouts.

**Implemented separation:**

- `public/lab.php` is a local-only, technician-authenticated course exercise page. It exposes a browser text editor with Open/Save buttons and a user-permitted folder monitor, plus a Philippine public holiday reference. None of these lab interactions changes repair tickets or discloses customer records.
- `public/assets/lab.js` uses file I/O event handlers and `CustomEvent` observers. It uses **browser File System Access APIs**, not .NET `FileSystemWatcher`. Directory polling is active **only while the page is open** and when the user explicitly chooses a folder. No local files are uploaded to PHP.
- `labs/NotepadCompanion/` is the **C# Windows Forms source** using actual `OpenFileDialog`, `SaveFileDialog` and `.NET FileSystemWatcher` in the same academic repository. Its .NET 8 source is **compiled in a separate Windows GitHub Actions job**. Real OS watcher events, desktop interaction and installation still require an actual Windows manual run.
- `public/holiday-api.php` uses an authenticated technician session to fetch Philippine national public holidays from a **fixed** HTTPS endpoint of Nager.Date. The server parses and validates JSON; the browser fetches the server's JSON asynchronously and renders only escaped text through DOM node methods. The holiday reference is **not branch opening hours**. Unavailable third-party API returns a nonfatal message and does not stop repair work.

## Automated verification

- `php course-edp/tests/edp-lab.php` tests JSON parsing, filtering, date checks, year bounds, and malformed/oversized response rejection **without calling an external server**.
- `python3 course-edp/tests/browser-hci.py` runs real headless Chrome/Chromium against the actual disposable MySQL-backed localhost PHP app. It checks intake, manager, technician, cashier and customer login pages at **375/768/1366 px**, screenshots role home/empty states, checks horizontal overflow and required labels, and exercises the authenticated Notepad Open/Save and mocked JSON display. Only fictional staff accounts are generated by the established test fixture. This is **not** a substitute for a manual screen-reader and real-device evaluation.
- `./.github/workflows/edp-schema.yml` runs the existing SQL, concurrency, role-specific, and cross-role HTTP tests **before** the browser acceptance gate. It uploads browser screenshots as a workflow artifact.
- The UI JSON rendering test intercepts the network request with a **fictional** response. It confirms event/DOM handling but does **not** prove that the third-party Nager.Date service is online at any given moment.

## Required manual acceptance before submission

1. Open `public/technician.php` on a disposable local MySQL instance, sign in as a fictional technician, and select **EDP Lab Tools**.
2. Save a `.txt` file from the web editor, reopen it, and confirm the content. Select a local folder and create a second `.txt` file. Confirm the monitor lists its creation; then stop monitoring. Try a browser lacking File System Access and confirm the fallback message.
3. On **Windows with .NET 8**, run the included WinForms source. Open and save a `.txt` file, then create/rename a `.txt` in the watched folder and capture the `FileSystemWatcher` notification. Do not mark this check complete without that Windows run.
4. Click **Check holiday reference**. Observe either a valid holiday list with source label or an understandable, nonblocking error when offline. Never infer branch opening hours from third-party dates.
5. Examine the GitHub Actions browser screenshots at mobile, tablet, and desktop sizes; manually check touch targets, keyboard focus, screen reader labels, contrast, zoom to 200%, and text overflow. Automated checks cover only a subset of accessibility.

## Security boundaries

Keep localhost-only enforcement, role checking and separate customer sessions. API input is only the current or next year; no caller-controlled URL. Browser-local note files never enter the database. The Windows companion has no database credentials. Never upload customer media or signatures into the lab. Do not deploy using the CI database's `root` account or assume a 5-hex portal code plus four-digit PIN is sufficient for a public site.
