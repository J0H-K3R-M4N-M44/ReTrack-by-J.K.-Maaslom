# EmailJS and notification delivery

This feature keeps three destinations separate:

1. **Customer email outbox** — repair updates and cash-payment notices sent only to a customer email address with a recorded permission timestamp.
2. **Staff in-app inbox** — recipient-specific notifications shown inside the staff workspace.
3. **Staff email outbox** — optional EmailJS copies of the staff inbox events, routed to the same authorized staff recipients.

Password-reset messages are sent immediately through their own EmailJS template. Reset tokens are generated by PHP, stored only as hashes in MySQL, expire after 30 minutes, and are never written to either notification outbox.

## 1. Configure EmailJS

This project uses **two EmailJS templates total**:

1. **Password reset** — immediate staff-account recovery email.
2. **RepairTrack notification** — one flexible template for customer repair updates, customer payment notices, and optional staff alerts.

In your EmailJS account:

- Connect and test the sender email service.
- Create the two templates from the HTML files in `docs/emailjs-templates/`.
- Set **To Email** to `{{to_email}}`, **To Name** to `{{to_name}}`, and **Subject** to `{{subject}}` in both templates.
- Copy the service ID, public key, private key (optional), and the two template IDs into your local ignored config.
- Keep staff email disabled until staff content and recipient routing have been tested with synthetic accounts.

Do not commit EmailJS keys or template IDs. Add them only to the Git-ignored `config/config.php`, using `config/config.example.php` as the shape:

```php
'emailjs_public_key' => 'YOUR_PUBLIC_KEY',
'emailjs_private_key' => 'YOUR_PRIVATE_KEY',
'emailjs_service_id' => 'YOUR_SERVICE_ID',
'emailjs_staff_notifications_enabled' => false,
'emailjs_templates' => [
    'password_reset' => 'YOUR_PASSWORD_RESET_TEMPLATE_ID',
    'notification' => 'YOUR_NOTIFICATION_TEMPLATE_ID',
],
```

The private key is optional in EmailJS requests; keep it server-side if you use it. Never place any key in HTML, JavaScript, source control, screenshots, or a customer-visible page.

## 2. Template variables

The PHP code still uses the logical names `customer_update`, `customer_payment`, and `staff_alert` in its outboxes. The sender maps all three names to the single `notification` template ID. This keeps the queue records readable without consuming extra EmailJS templates.

### `password_reset` template

- `to_email`, `to_name`, `subject`
- `reset_url`
- `expires_minutes`

The reset URL is generated by PHP from a random, one-time token. The database stores only the token hash. Do not pass the token to the notification template or log it.

### `notification` template

Common recipient fields:

- `to_email`, `to_name`, `subject`

Customer repair update fields:

- `show_customer_update` (boolean), `customer_name`, `ticket_code`, `device_label`
- `status`, `message`, `branch_name`, `branch_phone`

Customer payment fields:

- `show_customer_payment` (boolean), `customer_name`, `ticket_code`
- `payment_amount`, `remaining_balance`, `branch_name`

Staff alert fields:

- `show_staff_alert` (boolean), `event_type`, `title`, `message`
- `ticket_code`, `branch_name`, `target_url`

The server sets exactly one `show_...` flag to `true` for each notification. The HTML uses EmailJS conditional sections (`{{#flag}}...{{/flag}}`) so unrelated sections are omitted. A missing or false flag does not render its section. Do not use triple-brace variables for untrusted message content; double-brace fields are HTML-escaped by EmailJS.

Customer updates contain only the customer-visible status summary. Internal notes, serial numbers, photos, private tracking PINs, staff names, and storage locations are not sent. Customer payment mail is informational, not a tax invoice, payment gateway receipt, or COD confirmation. Staff messages omit customer contact details, PINs, private technician notes, and evidence files.

## 3. Customer email permission

At intake, staff may select **Email** and tick:

> I have the customer's permission to email repair updates to this address.

The checkbox is optional and unchecked by default. The system records the permission timestamp and sets the notification preference only for an email contact when that box is checked. Phone contacts do not qualify.

For existing databases, the migration adds a separate `email_updates_consent_at` field. Old `preferred_for_notifications` values alone are not sufficient: without the new permission timestamp, customer emails are not queued. Existing customer details are not overwritten by intake edits. A separate customer-contact preference screen can be added later if customers need to change their choice themselves.

## 4. Staff routing

Staff in-app notifications are always stored per user. Admin is global; every other staff member must be active and assigned to the relevant active branch. VIEWER is deliberately excluded.

| Event | Staff recipients |
|---|---|
| New ticket issued | Admin, manager and intake agent for the branch |
| Estimate shared or customer decision recorded | Admin, manager and intake agent; the assigned technician receives decision alerts |
| Repair stage changed | Admin and branch manager |
| Device ready for pickup | Admin, manager and cashier |
| Repair closed / returned | Admin, manager, intake agent and cashier |
| Technician assignment | Only the technician who was assigned |
| Final bill issued / counter cash received | Admin, manager and cashier |
| Device transfer dispatched, received, or exception | Admin, managers and couriers assigned to the sending or receiving branch |
| Repair responsibility accepted at destination | Admin and managers at the origin/destination branch; branch couriers also see the transfer event |

Technicians do not receive every device's status alert; they receive assignment and relevant customer-decision notifications for their assigned repairs. Cashiers do not receive technician-only notes. Couriers do not receive estimates or cash details. The staff email outbox uses the same recipient set as the staff inbox.

## 5. Delivery worker (Windows/XAMPP)

Customer and staff emails are queued by application actions. The CLI worker sends them through EmailJS with one shared rate limit for both queues.

Run a small test batch from Git Bash:

```bash
/c/xampp/php/php.exe tools/send-notifications.php --limit=2
```

For routine operation, use Windows Task Scheduler to run the command on a short interval (for example, every 2–5 minutes) while MySQL and the local PHP environment are available. Run only one scheduled worker instance at a time. On a hosted environment, configure the host's approved cron facility instead.

The worker:
- Sends up to the configured batch size from each outbox.
- Uses a shared local lock to enforce the EmailJS one-request-per-second limit.
- Retries failed deliveries with increasing delays and stops after five attempts.
- Recovers stale `SENDING` rows left by an interrupted worker.
- Logs only delivery status/error details, not reset tokens or template contents.

A successful run is not proof that the recipient received or read the email. Check the EmailJS dashboard and test each template with synthetic addresses before real use. Do not use real customer email addresses in development fixtures.

## 6. Database upgrade

Back up first, pause application writes, and inspect the configured database:

```bash
/c/xampp/php/php.exe tools/migrate.php
```

Then, only against the intended isolated/test database after reviewing the pending list:

```bash
/c/xampp/php/php.exe tools/migrate.php --apply
```

The `notifications_emailjs.sql` migration creates the separate staff/customer inbox/outbox tables and adds the customer email-consent timestamp. Fresh installs receive the same structures from `database/schema.sql`.

## 7. Release checks and limitations

Test the password-reset template using a synthetic staff account, then test customer updates with both opted-out and opted-in synthetic customer contacts. Verify no customer email is queued for a contact without a consent timestamp. Verify staff notifications for two branches, two technicians in one branch, a cashier, a courier, an administrator, and a read-only viewer.

EmailJS is a low-volume template sender, not a transactional email platform or an application notification inbox. For production use, confirm account quotas, sender-domain verification, data-retention needs, unsubscribe/consent handling and delivery reliability. The staff in-app inbox remains available if staff email is disabled or unavailable.
